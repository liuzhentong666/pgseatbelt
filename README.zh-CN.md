# pgseatbelt

[English](README.md)

**Postgres 的安全带。** 它限制 AI Agent 自己的 PostgreSQL 登录能对已有应用的表做什么，即使 Agent 自己写 SQL 也一样，而且不需要改动应用。就像安全带一样，它不妨碍正常工作，只在出问题时限制损害：一再越过限制的 Agent 会被停用，它改过的数据可以回滚到出问题之前的状态。

在数据库内部它用一个简称 `guard`：`guard` 模式、`guard.sql`、`guard.py`，以及角色 `guard_worker`、`guard_keeper` 和 `guard_broker`。

**状态：** 原型（2026-11-14）。只在一台笔记本上用下面的攻击套件测试过，只由编写它的助手审查过，尚未用于真实数据。

## 为什么需要它

Agent 在执行普通任务时，删除或改写过没有人让它碰的数据。依赖有人盯着、或依赖 Agent 表现良好的规则，挡不住这种事。这个防护把限制放在 Agent 的数据库登录本身上：由固定代码决定，记下谁改了什么，并让改动可以撤销。

## 它做什么

- **每个 Agent 有自己的登录。** `guard.py run` 发放一个登录：会过期，持有 `guard_worker`，记录每条语句，并且不能提高自己的限制或权限。Agent 直接写应用的表。
- **每次写入都受限制。** 每张受保护的表上都有触发器，扣除该登录的行预算和字节预算。预算在发放时固定，不能追加（AB002、AB003）。冻结时（AB000）或不在 READ COMMITTED 隔离级别下（AB006）的写入会被拒绝，TRUNCATE 会被拒绝，每处改动都以该登录的名字记入 `guard.audit`。
- **先声明，再动手。** 不事先说明时，一个登录只能改动一张表的一小部分：它的前 20 行，之后是这张表的十分之一；在前 20 行以内，最多改动原有行的一半。要改得更多，Agent 先声明它打算改动这张表的多少行：`SELECT guard.declare('shop.orders', 500);`，之后就以这个数字为准。没有声明的大改动会被拒绝，拒绝信息会说明怎样声明，这不算越界（AB009）。超过自己声明行数的语句会被拒绝，并记一次越界（AB007）：这正是那种碰到的行远比本意多的语句，例如丢了 WHERE 的 UPDATE。这个数字是 Agent 自己定的，所以它挡不住存心搞破坏的 Agent；能挡住的是预算，以及 `--max-table-share` 设的上限，Agent 声明什么都抬不高这个上限。
- **提交时再检查一次。** 在冻结之前做的写入，不能在冻结之后提交。这次检查会持有一把锁，冻结要等这把锁；如果某个 Agent 事务提前触发了这次检查（`SET CONSTRAINTS ... IMMEDIATE`），冻结会直接结束它，不论看守程序是否在运行。
- **越界计次，到数即停。** 每次因试图越过限制而被拒绝（AB002、AB003、AB007），都给该登录记一次越界，拒绝信息会告诉 Agent 还剩几次。捕获这个错误或回滚事务，都抹不掉这次记录。记到最后一次时（默认 3 次），该登录被停用（AB001）：它不能再写入任何东西，最后一次越界所在的事务什么也留不下，看守程序会结束它的会话，`run` 会收回它的连接权限。
- **撤销与报告。** `undo` 从最新的开始把一个登录的改动放回去，只检查它改过的列。别人之后改过的行保持原样（AB005），结果会写出这一行以及是谁改的；其余的都放回去。它可以撤销该登录做过的一切，也可以只回到某个点、保留这个点之前的工作：该登录的第一次越界，或它的任何一个事务。一起列出的几个登录，会按它们全部改动从新到旧的顺序一起撤销，彼此不会挡路。`report` 从审计日志得出一个登录改了什么，并给出它的越界次数和按顺序排列的事务。两者都会拒绝从未发放过的登录名，所以打错的名字不会被读成“什么也没改”。
- **看守程序。** 它的自检读取系统目录，发现任何问题就冻结 Agent 的写入。它会结束卡住的 Agent 会话：登录已过期、登录已停用、冻结时仍在写入、持有表锁、事务空闲 60 秒或开启 300 秒、空闲时持有咨询锁。只有数据库属主能解冻。
- **应用保持原样。** 应用自己的登录不受限制，也不被记录。不过它对受保护表的每次写入仍要经过触发器代码，实测每行多约 40 微秒。

## 使用

以数据库的超级用户属主身份，保护 Agent 可以写的表：

```
python guard.py install --database APP_DB --protect shop.products --protect shop.orders
```

然后授予 `guard_worker` 对 Agent 可读内容的 SELECT 权限。Agent 可以调用的 SECURITY DEFINER 函数，读过之后再允许：`SELECT guard.allow('shop.restock(bigint,integer)', '原因');`。

```
python guard.py run --database APP_DB --rows 1000 --bytes 10000000 --hours 8 [--max-table-share 0.2] [--strikes 3] [--undo-on-stop] -- <Agent 的命令>
python guard.py keep --database APP_DB
python guard.py status --database APP_DB
python guard.py report --database APP_DB LOGIN [--timeline]
python guard.py undo --database APP_DB LOGIN [LOGIN ...] [--since-strike | --from CHANGE]
python guard.py freeze --database APP_DB "原因"
python guard.py unfreeze --database APP_DB
python guard.py backup --database APP_DB --to FOLDER
python guard.py unprotect --database APP_DB shop.orders
python guard.py uninstall --database APP_DB --audit-to FOLDER [--drop-roles]
```

连接设置来自 `connection.local.json`（复制 `connection.example.json` 得到）。每条命令都必须写 `--database`。

在真实应用上安装之前：

- 安装需要超级用户。其他角色安装会被拒绝，并且什么也不改，因为那样装出来的防护看起来完整却不能用：看守程序结束不了任何会话，发放程序发放不了任何登录。不提供超级用户的托管服务目前还不能运行它。
- 安装会撤销 PUBLIC 对该数据库的 CONNECT 和 TEMPORARY 权限，以及创建大对象的权限，所以依赖这些权限的登录需要先有自己的授权。
- 受保护的表必须有主键。分区表作为一张表受保护：它的限制、审计记录和撤销都以整张表为准，不管某一行在哪个分区里；之后新增的分区也会被覆盖。Agent 通过这张表写入，不能直接写某个分区。单独的一个分区，以及被其他表继承的表会被拒绝，因为防护的触发器覆盖不到它们。最好使用 bigint 键，因为 Agent 可以耗尽序列值。
- 保护一张表时，Agent 可以使用这张表的行取值所用的序列：列自己拥有的序列（`serial`、标识列），以及列的默认值里写明的序列（转储出来的表结构常常是这样）。Agent 只能取下一个值，不能设置序列。只在默认值调用的函数内部用到的序列不会被发现，需要你自己把它的 USAGE 授予 `guard_worker`。给受保护的表新增默认值之后，请重新运行 `install`。
- 保护一张表时，最多等它的锁 2 秒；表正忙时会失败且什么也不改，而不是挡住应用。再运行一次即可。重新运行安装，会把已受保护的表更新到当前的触发器。
- 能使用 shell 的 Agent 必须运行在容器里或单独的操作系统账户下：在其中运行 `python check_sandbox.py` 检查。

## 当 Agent 出问题时

**防护自己发现。** 试图越过限制的操作会被拒绝，所以它什么也没改，同时记一次越界。记满次数的登录会立刻在数据库内部被停用。`run` 随后收回它的连接权限，在 stderr 上报告这次停用；如果 Agent 的命令本身以 0 退出，`run` 以 3 退出。加上 `--undo-on-stop`，`run` 还会撤销该登录自第一次越界以来的改动，也就是回到它第一次越过限制之前的状态。第一次越界之前的改动保留。不加这个选项时，在你下令之前什么都不会撤销：

```
python guard.py undo --database APP_DB LOGIN --since-strike
```

**你自己发现。** Agent 可能在限制之内做错事，这时不会有越界记录。列出它的事务，找到第一个出错的事务，从那里开始撤销。每个事务都列有它第一处改动的编号，`--from` 用的就是这个编号：

```
python guard.py report --database APP_DB LOGIN --timeline
python guard.py undo --database APP_DB LOGIN --from CHANGE
```

不带选项的 `undo` 会放回该登录做过的一切。任何形式的 `undo` 都会先停止该登录，在登录退役后仍然可用。它可以用于带生成列的表（生成列由 PostgreSQL 重新计算），并把被删除的行按原来的标识值放回去。

**几个 Agent 改过同样的行时。** `undo` 从不覆盖更新的工作。之后被别的东西（另一个 Agent、应用程序或人）改过的行保持原样，该登录对这一行更早的改动也一样保持原样；其余的都撤销。结果会列出它留下的每一行以及之后是谁改的（`conflicts`、`blocked_by`），还会列出只撤销了一部分的事务（`partly_undone_transactions`）：请检查这些事务，因为它们原本一起完成的事现在只剩一部分。要把剩下的也撤销，先撤销挡路的 Agent，或者手工处理那些行，然后再运行一次 `undo`。一起列出的几个 Agent 会按它们全部改动从新到旧的顺序撤销，这个顺序不会让任何一个挡住另一个：

```
python guard.py undo --database APP_DB LOGIN_A LOGIN_B
```

## 当应用的表结构变化时

受保护的表在防护之下发生变化时，自检会发现；和其他问题一样，看守程序的下一轮会冻结 Agent 的写入。由属主处理，然后运行 `unfreeze`。

- **受保护的表被删除了。** 问题信息会写出它的名字。运行 `python guard.py unprotect --database APP_DB shop.orders`，表示这次删除是有意的。`report` 仍然能写出这张表的名字；`undo` 会跳过对它的改动（已经没有办法放回去），并在 `dropped_tables` 中计数。
- **它的主键变了。** 重新运行 `install`，它会按新的主键重建这张表的触发器。如果某处改动是按已经不再是主键的键记录的，`undo` 会以 AB005 留下这处改动，因为那个键现在可能对应多行。
- **它变成了另一张表的分区、被其他表继承，或者失去了主键。** 它不能再受保护：把它改回原样，或者用 `unprotect` 把它移出防护。

`unprotect` 也用来有意地把一张表移出防护。防护的触发器会被删除，`guard_worker` 在这张表以及只有它使用的序列上得到的全部授权（包括读取）也会被收回，所以 Agent 不能再写它。它的审计记录保留，`undo` 仍然能把这些改动放回去。

## 卸载

以超级用户属主身份运行 `guard.py uninstall`，从一个数据库中移除防护：

1. 冻结 Agent，并结束它们的会话。
2. 把审计日志、撤销记录和预算逐行写入 `--audit-to` 目录下的一个 JSON 文件，所以很大的日志也能保存。这个文件是 Agent 做过什么的唯一记录。
3. 在一个事务中：删除防护的触发器，撤销在该数据库中授予三个防护角色的所有权限（表及其列、序列、函数和过程、模式、类型、大对象，以及默认权限），把 PUBLIC 的权限恢复到第一次安装之前的样子（当时记录在 `guard.installed_over` 中），并删除 `guard` 模式。对每张受保护的表，最多等它的锁 2 秒。任何一步失败，都什么也不改，防护仍然装着，并保持冻结。

Agent 改过的数据保持原样，所以需要恢复的内容，请先运行 `undo`。如果防护之外有东西依赖它（例如建在 `guard.audit` 上的视图），卸载会被拒绝，并且什么也不改，因为删除模式会把它一起删掉。

不加 `--drop-roles` 时，三个角色和 Agent 登录仍留在服务器上。这些登录不能再写入，但在 PUBLIC 可以连接的地方仍能连接。加上 `--drop-roles`，这些角色和登录也会在同一个事务中被删除；如果同一服务器上还有别的数据库在用这些角色（还装着防护，或者那里给它们授予了什么），这一操作会被拒绝，并且什么也不改。

## 证据

`python tests/check_guard.py` 会新建一个带有应用表结构和数据的临时数据库，安装防护，并用真实的登录和真实的连接攻击它。攻击来自 Forkpoint 的边界攻击套件（1273af5 的 `scripts/agent_login_attacks.py`），逐组移植，另加一组复查攻击：COPY、upsert、MERGE、可写 CTE、在循环中调用特权函数，以及被应用触发器跳过的更新。一个有相同授权但不持有 `guard_worker` 的普通登录，必须能完成同样的数据攻击，以证明这些攻击本身有效。

另有一组越界检查，验证停用和回滚：登录在最后一次越界时被停用，那次越界所在的事务什么也留不下，捕获错误抹不掉越界记录，Agent 碰不到自己的计数，看守程序会结束已停用登录的会话，`undo` 能回到第一次越界之前或选定的事务之前。同样的内容也通过 `guard.py run`、`report` 和 `undo` 检查了一遍。

还有一组生命周期检查，在防护之下改动表结构。保护单独的一个分区、被其他表继承的表或没有主键的表会被拒绝；之后新增的子表、改变了的主键和被删除的表都会被发现；`undo` 会留下按已不存在的主键记录的改动，主键恢复后再完成它，并会跳过已删除的表；只有属主能 `unprotect`；从未发放过的登录名会被拒绝；以非超级用户角色安装会被拒绝，并且什么也不改。

撤销检查还覆盖了带生成列的表、标识值总是由数据库生成的表，以及数据库拒绝放回的改动（AB008）：撤销会留下这处改动、完成其余部分、给出数据库的报错，原因消除后可以完成。当别的 Agent 和属主之后改过其中一些行时，撤销只留下这些行以及该 Agent 对它们更早的改动，其余都撤销，写出每一行以及之后是谁改的，列出只撤销了一部分的事务，并在别人的改动撤销之后把剩下的也撤销；一起列出的两个 Agent 会按两者改动从新到旧的顺序被完整撤销。

还有一组序列检查：受保护的表从列默认值里写明、但不属于任何列的序列取编号，其中一个序列在另一个模式里。Agent 的插入能从默认值取到编号，Agent 仍然不能设置序列，取消保护其中一张表时，另一张受保护的表仍在使用的序列会保留。

还有一组分区检查，把分区表作为一张表来保护：Agent 通过这张表写入，不能直接写某个分区；份额以整张表计算；每处改动（包括在分区之间移动的行）都记在这张表名下，撤销能全部放回；之后新增或删除分区不算问题，新分区同样受保护；某个分区上的防护触发器被禁用会被发现。

还有一组声明检查，使用没有上限的登录：额度之内的改动不需要声明；更大的改动会被拒绝但不记越界，并说明怎样声明；先声明之后就能通过；超过声明行数的改动，以及没有 WHERE 的 UPDATE，会被拒绝并记越界；清空一张小表需要先声明，并且可以撤销；Agent 声明什么，都抬不高操作者设的上限，也撑不大预算。

2026-11-14 的结果（`results/attack-results.json`）：377 项成立，16 项 NOTE，0 个缺口；之后所有测试数据库、角色和登录都已删除。没有移植的组需要 Forkpoint 的分支才有意义：读集合入，以及对文件、提交和历史的检查。对应关系和更早的运行记录在本地的 forkpoint-experiments 仓库中（`experiments/guard_full_suite`、`experiments/boundary_without_branches`）。

`python tests/check_uninstall.py` 在两个临时数据库中安装防护，让一个 Agent 登录在每个库里各改一行，然后卸载。一个库是 PostgreSQL 的默认权限；另一个库的属主事先已经收回了 PUBLIC 的 CONNECT、TEMPORARY 和创建大对象的权限。工作角色还会得到一张表部分列上的授权、一个过程，以及默认权限；另有一张受保护的表从另一个模式里的序列取编号。卸载必须把每项权限、每个模式和每个触发器原样恢复，按权限的含义比较；有视图依赖防护时，卸载必须拒绝。之后第一个库在删掉一张受保护的表之后再安装、卸载一次；最后一次卸载通过命令行并带 `--drop-roles` 运行，而在另一个库还给这些角色授予着东西时，它必须先被拒绝。2026-11-14 的结果（`results/uninstall-results.json`）：17 项成立，0 个缺口。

## 测试环境

只在下面这个环境中测试过（2026-11-09 至 2026-11-14）：

- 一台 Windows 11 笔记本（版本号 26200）。
- PostgreSQL 16.15，即 Ubuntu 24.04.2 的软件包，运行在 WSL 2 中（2.6.3，内核 6.6.87.2）。
- Windows 上的 Python 3.10.11 通过 `wsl.exe` 调用 WSL 内的 psql 16.15。
- 属主通过 Unix 套接字连接；Agent 登录用 SCRAM 口令连接 127.0.0.1。

需要 PostgreSQL 16 或更高版本，因为它用到了 16 的角色选项。目前只试过 16.15。

## 它不做什么

- **不保护读取。**
- **不判断改动的含义。** 它唯一视为异常的行为，是试图越过发放登录时定下的限制，或越过它自己声明的行数。在限制之内造成破坏的 Agent 不会被记越界：需要人来发现，再用 `undo --from` 放回去。
- **停用有边界情况。** 持有锁不记越界。只运行 `keep`、不通过 `run` 时，已停用的登录仍能连接和读取，直到看守程序的下一轮结束它的会话。服务器崩溃后，已有越界记录的登录，次数可能多出最多 32 次，从而被停用。
- **可用性。** Agent 能拖慢应用：它可以持有某些行，直到看守程序的 60 秒或 300 秒规则结束它的会话；可以锁住整张表直到看守程序的下一轮（或让应用的读取排在它等待的锁后面）；重新连接后还能再这样做，直到登录过期或被停止。
- **没有暂存。** Agent 的写入在提交时就生效。避免读到过期数据是 Agent 自己的事（`SELECT ... FOR UPDATE`）。
- **撤销有缺口。** 它会留下放不回去的改动，以及该登录对同一行更早的改动：别人之后改过的行，或表已不再使用的主键（AB005），或数据库自己拒绝的改动，例如之后新加的约束（AB008，附带数据库的报错）。它只认得行，不知道这些行合在一起是什么意思，所以撤销其余部分可能让一个事务只撤销了一部分，或者让一个之后的改动（这个 Agent 的或别人的）建立在一个已被撤销的改动之上；结果会列出只撤销了一部分的事务，除此之外没有别的提醒。原因解决后重新运行，会把留下的也撤销。对之后被删除的表的改动完全无法放回。之后新增的列，在撤销放回的行里取默认值。没有命令能重做被撤销的改动，所以 `--undo-on-stop` 是可选项而不是默认行为。它只回到该登录的第一次越界，不会更早。
- **表结构的变化只能被发现，不能被阻止。** 从受保护的表发生变化到看守程序的下一轮之间，防护就停留在变化之后的样子。例如，属主让一张表继承某张受保护的表之后，可以通过父表写入这张子表的行，既不扣预算也不留记录，直到那一轮冻结写入为止。
- **需要信任的部分。** 发放程序、看守程序和属主的凭据必须放在 Agent 碰不到的地方。
- **尚未测试：** 原生 Linux 或 macOS 上的 psql、PostgreSQL 17 或更高版本、通过 TLS 连接的远程服务器、多级分区的表、真实容器、第二台机器，以及外部审查。
